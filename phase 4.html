Traditional versus Web-Based Systems Development

10.1.1 Traditional Development

ماذا سندرس؟

في Traditional Development يهتم الفريق بدرجة كبيرة بـ:

  • Compatibility
  • Existing Hardware
  • Existing Software
  • Legacy Systems
  • Company LAN/WAN
  • Existing Infrastructure
  • Desktop Resources
  • Security داخل بيئة المؤسسة

وقد يتم الحصول على النظام عبر:

  • 1. In-House Development
  • 2. Purchasing a Software Package
  • 3. Hiring Consultants / External Resources

الفكرة الأساسية

في هذا النوع تكون Web Features غالبًا جزءًا إضافيًا وليست بالضرورة المنصة الأساسية للنظام.

أهم المصطلحات

Traditional DevelopmentLegacy SystemCompatibilityIn-House DevelopmentSoftware PackageConsultantScalabilitySecurity

لماذا مهم؟

لأن ليس كل مشروع يجب تحويله إلى Web System.

قد تكون المؤسسة لديها:

  • Legacy Applications
  • Infrastructure موجودة
  • متطلبات داخلية
  • نظام لا يحتاج Web Component

فيكون Traditional Approach منطقيًا.

ماذا ستستفيد؟

💡

"الأحدث دائمًا أفضل."

10.1.2 Web-Based Development

ماذا سندرس؟

في Web-Based Development:

  • Web تصبح Platform أساسية.
  • التطبيقات يمكن أن تعمل عبر Hardware Environments مختلفة.
  • توجد قابلية أكبر للتوسع في كثير من الحالات.
  • Software قد يقدم كـService.
  • Vendor قد يتولى Installation وConfiguration وMaintenance.
  • Integration وSecurity تصبحان قضايا مهمة جدًا.

أهم الأفكار

Web-Based System يمكن أن يعتمد على:

Browser / Web Client←Web/Application Services←Back-End Systems / Database

تحديات مهمة

Integration

قد تحتاج الأنظمة إلى:

Middleware

حتى تتكامل مع:

  • Existing Software
  • Legacy Systems
  • Different Platforms

Security

Internet Environment أكثر انفتاحًا، ولذلك توجد تحديات أمنية أكثر تعقيدًا.

مصطلحات مهمة

Web-Based DevelopmentMiddlewareScalabilitySaaSIntegrationInternet-Based Environment

10.4

Outsourcing

🔴 مهم

ما هو Outsourcing؟

الاعتماد على Third-Party Vendor لتنفيذ جزء أو كل العمل.

قد تستخدم المؤسسة Outsourcing حتى:

  • تخفض التكاليف.
  • تصل إلى خبرات متخصصة.
  • تركز على Core Business.
  • تحصل على موارد لا تملكها داخليًا.

10.4.1 The Growth of Outsourcing

ماذا ندرس؟

لماذا توسع Outsourcing؟

من الأسباب التي يناقشها الفصل:

  • Cost Effectiveness
  • Global Talent
  • Specialized Expertise
  • Focus on Core Functions

10.4.2 Outsourcing Fees

الفصل يشير إلى عدة Fee Structures.

منها:

Fixed Fee Model

سعر متفق عليه.

Time and Materials

التكلفة تعتمد على الوقت والموارد.

Outcome-Based Models

الدفع مرتبط بنتائج أو Outcomes.

لماذا مهم؟

نموذج الدفع يؤثر على:

  • Risk
  • Cost
  • Contract Management

10.4.3 Outsourcing Issues and Concerns

لا ننظر إلى Outsourcing على أنه:

💡

أرخص = أفضل.

ندرس مخاطر مثل:

  • Quality Control
  • Data Security
  • Dependence on Vendor
  • Third-Party Risk
  • Loss of Control
  • Communication
  • Service Quality

10.5

Offshoring

🟢 فهم قوي

Offshoring

نوع من Outsourcing يتم فيه نقل Services إلى Country أخرى.

لماذا تستخدمه المؤسسات؟

قد تحصل على:

  • Lower Labor Costs
  • Global Talent
  • 24-Hour Work Possibility عبر Time Zones

المخاطر والتحديات

  • Time Zone Differences
  • Cultural Differences
  • Communication Barriers
  • Data / Intellectual Property Security
  • Different Legal Environments
  • Project Control
  • Public / Employee Backlash

مصطلح مقابل

Reshoring / Onshoring

إعادة الأنشطة إلى البلد الأصلي أو أقرب إلى المؤسسة بعد أن كانت Offshore.

ماذا ستستفيد؟

ستعرف الفرق بين:

Outsourcing

و:

Offshoring

فليس كل Outsourcing = Offshoring.

Software as a Service — SaaS

🔴 مهم

من أهم المفاهيم الحديثة في الفصل.

Software Vendor يبيع License.

ثم العميل يتحمل مسؤولية:

  • Installation

  • Patches
  • Technical Issues

SaaS Model

غالبًا يكون التسعير:

Subscription-Based

والـProvider يتولى قدرًا أكبر من:

  • Hosting
  • Maintenance
  • Updates
  • Infrastructure

10.6.1 Advantages

الفصل يبرز مزايا مثل:

  • Scalability
  • Ease of Use / Deployment
  • Reduced In-House Infrastructure
  • Subscription Model
  • Vendor-Managed Service

10.6.2 Shortcomings

نحتاج أيضًا التفكير في:

  • Vendor Dependence
  • Security / Privacy
  • Integration
  • Long-Term Cost
  • Service Availability
  • Control

11.3.2 Cohesion and Coupling

من أهم مفاهيم Software Design.

Cohesion

مدى ترابط الأعمال الموجودة داخل Module واحدة.

الهدف:

💡

High Cohesion

أي أن Module تقوم بوظائف مرتبطة ببعض.

Coupling

مدى اعتماد Module على Modules أخرى.

الهدف:

💡

Loose / Low Coupling

حتى تكون الأجزاء:

  • أسهل للفهم.
  • أسهل للتعديل.
  • أسهل للصيانة.
  • أقل تأثيرًا على بعضها.

الفكرة الذهبية

💡

High Cohesion + Low Coupling

هذه قاعدة مهمة جدًا ستتكرر معك في Software Architecture وDesign.

11.9.2 System Changeover

من أهم مواضيع Installation.

السؤال:

💡

كيف ننتقل من Old System إلى New System؟

هناك أربع Strategies رئيسية.

1. Direct Cutover

نوقف النظام القديم.

ونبدأ الجديد مباشرة.

الميزة

  • سريع.
  • لا نحتاج تشغيل النظامين معًا.

المخاطرة

إذا فشل الجديد:

💡

قد لا يوجد بديل فوري.

Risk

مرتفع نسبيًا.

2. Parallel Operation

نشغل:

Old System + New System

في نفس الوقت لفترة.

الميزة

  • Risk أقل.
  • يمكن مقارنة النتائج.
  • القديم موجود إذا فشل الجديد.

العيب

  • مكلف.
  • يحتاج عملًا مضاعفًا.

3. Pilot Operation

نطبق النظام كاملًا على:

جزء محدد من المؤسسة

مثل:

  • Branch واحدة.
  • Department واحد.

إذا نجح:

نعممه.

الفكرة

💡

Entire System → Some Users / One Site

4. Phased Operation

نطبق النظام:

Module by Module

أو:

Phase by Phase

على المستخدمين.

مثال:

نبدأ Inventory.

ثم Sales.

ثم Accounting.

الفكرة

💡

Part of System → All / More Users

الفرق المهم

Pilot

النظام كامل.

لكن:

لجزء من المستخدمين أو Location واحدة.

Phased

جزء من النظام.

لكن:

ينفذ تدريجيًا على المؤسسة.

المستوى

🔴🔴🔴 إتقان كامل

Data Conversion

وقد نحتاج:

  • Mapping
  • Validation
  • Cleaning
  • Automated Conversion
  • Testing

لماذا مهم؟

نظام ممتاز + Data Conversion فاشلة = Implementation فاشلة.

🔴🔴 مهم جدًا.

  • Who?
  • What?
  • When?
  • How?
  • Materials?
  • Trainers?

الفصل يناقش أساليب مثل:

Train-the-Trainer

تعليم ذاتي موجه.

Online Training

تعلم تفاعلي.

Simulation

  • Practice
