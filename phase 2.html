CHAPTER 04

Requirements Engineering

هذا من أهم فصول الكتاب كله. نريد أن نجيب عن: «ماذا يحتاج العميل فعلًا؟» وليس فقط: «ماذا قال العميل إنه يريد؟» — هناك فرق كبير. الفصل يغطي جمع الحقائق، JAD، RAD، Agile، المقابلات، الملاحظة، الاستبيانات، User Stories، وتمثيل المتطلبات والتحقق منها.

4.1

System Requirements

🔴🔴 إتقان كامل

ما هو System Requirement؟

خاصية أو Feature يجب أن تكون موجودة في Information System حتى يحقق Business Requirements ويلبي احتياجات المستخدمين.

الأنشطة الثلاثة الكبرى لـ Requirements Engineering

  • 1. Gathering Requirements — نجمع المتطلبات. السؤال: ماذا يريد المستخدم؟
  • 2. Representing Requirements — نحول الكلام إلى Text، Diagrams، Models، User Stories، Scenarios.
  • 3. Validating & Verifying — نتأكد: هل المتطلبات صحيحة أصلًا؟ وهل تمت كتابتها بطريقة صحيحة وواضحة؟

4.1.1 أنواع المتطلبات

⚙️
Functional Requirements — تصف: ماذا يفعل النظام؟
النظام يسمح بتسجيل دخول المستخدم، يسجل عملية البيع، يطبع فاتورة، يحدث كمية المخزون، يعرض تقرير المبيعات.
📊
Non-Functional Requirements — تصف: كيف يجب أن يعمل النظام أو ما القيود والجودة المطلوبة؟
Response time أقل من 4 ثوانٍ، يدعم 25 مستخدمًا في نفس الوقت، يعمل طوال الأسبوع، يجب أن يكون آمنًا، يعمل على أكثر من Platform.

مصطلحات مرتبطة بالمتطلبات

  • Requirements Definitions — متطلبات موجهة بدرجة أكبر للمستخدم والجانب العام.
  • Requirements Specifications — وصف أكثر دقة يفيد Engineering Team.

لماذا Functional vs Non-Functional مهمة جدًا؟

لأن المبتدئ عادة يكتب: «User can add product» — وينسى:

Security Availability Performance Scalability Reliability Capacity

فتكون لديه Features، لكن النظام نفسه سيئ.

4.1.2 Requirements Challenges

  • 1. Imprecision — المتطلب غامض. مثال: «يجب أن يكون النظام سريعًا.» ما معنى سريع؟ 1 ثانية؟ 5 ثوانٍ؟ 30 ثانية؟
  • 2. Agreement — قد يقول المدير شيئًا، ويقول الموظف شيئًا آخر. السؤال يصبح: على ماذا نتفق؟
  • 3. Creep — وخاصة Feature Creep. المشروع يبدأ بعشرة Features، ثم «أضيفوا هذه فقط»، ثم «وهذه بسيطة»، فتتضخم المتطلبات.

خصائص Requirements الجيدة

Complete Consistent Clear Realistic Verifiable Traceable Understandable

4.1.3 Additional Considerations

  • Scalability — هل يستطيع النظام التعامل مع النمو؟ اليوم: 100 Order يوميًا. بعد سنتين: 20,000 Order. هل يستطيع؟
  • Security — ليس شيئًا نفكر فيه بعد انتهاء النظام. يجب أن يدخل في Requirements من البداية.
  • Total Cost of Ownership — TCO — لا ننظر فقط لتكلفة «كم سيكلف بناء النظام؟»، بل أيضًا: Hosting، Maintenance، Support، Hardware، Training، Upgrades، Downtime، Licensing.

4.2

Team-Based Techniques

🟢 مهم

4.2.1 JAD — Joint Application Development

يجتمع: Users، Managers، Systems Analysts، IT People في Sessions منظمة لاكتشاف ومناقشة Requirements.

👥
فائدته: بدل أن يقول مستخدم شيئًا للمحلل، ثم يقول المدير شيئًا مختلفًا، ثم يحاول المحلل التوفيق لاحقًا — نجمع الأطراف ونتناقش معًا.
Participants Session Goals Communication Agreement Documentation

4.2.2 RAD — Rapid Application Development

أسلوب Team-Based يهدف إلى تسريع التطوير واستخدام Feedback ونماذج تعمل بسرعة أكبر. نفهم علاقته بـ: Requirements، Users، Prototypes، Rapid Feedback.

4.2.3 Agile Methods

نرجع إلى Agile لكن هذه المرة من منظور Requirements: كيف نجمع Requirements في مشروع يتغير باستمرار؟

4.3

Requirements Elicitation

🔴🔴 أساسي

مصطلح مهم جدًا

Elicitation ليست مجرد: «اسأل العميل ماذا يريد.» بل عملية اكتشاف واستخراج Requirements.

والكلمة مهمة لأن العميل أحيانًا:

  • لا يعرف بالضبط ماذا يحتاج.
  • لا يستطيع التعبير عنه.
  • ينسى حالات مهمة.
  • يفترض أشياء يعتبرها بديهية.
  • يطلب Solution بدل شرح Problem.

Fact-Finding Plan

سنتعلم كيف نخطط لجمع المعلومات:

ماذا نريد أن نعرف؟ ← ممن سنجمعها؟ ← ما الطريقة المناسبة؟ ← متى؟ ← كيف نوثق؟
4.4

Interviews

🔴🔴 إتقان عملي

قبل المقابلة

من سنقابل؟ لماذا؟ ما Objectives؟ ما Questions؟

أنواع Questions

💬
Open-Ended Questions — «كيف تتم عملية البيع حاليًا؟»
تعطي الشخص حرية الشرح.
✅
Closed-Ended Questions — «هل يستطيع الموظف إلغاء الفاتورة؟ نعم أم لا؟»
📏
Range-of-Response — «كم طلبًا تعالجون يوميًا؟» أو «قيّم النظام من 1 إلى 5.»
⚠️
Leading Questions — أسئلة تقود الشخص نحو إجابة معينة. يجب الحذر منها.

Engaged Listening

لا تكون المقابلة: سؤال → جواب → السؤال التالي. بل:

استمع اسأل Follow-up افهم السياق لاحظ التناقضات

4.7

Representing Requirements

🟢 مهم جدًا

4.7.1 Natural Language

نكتب Requirements بالنص. مثال: «النظام يجب أن يسمح للمدير بإنشاء مستخدم جديد.»

⚠️
المشكلة: Natural Language قد يكون Ambiguous، Inconsistent، Incomplete. لذلك نحتاج أيضًا Diagrams وModels.

4.7.2 Diagrams

  • Functional Decomposition Diagram — FDD — نقسم Function كبيرة إلى وظائف أصغر.
    مثال: Order Management → Create Order، Modify Order، Cancel Order، Track Order.
  • Business Process Diagrams — تمثيل عمليات العمل.
  • DFD — سنأخذها بالتفصيل في Chapter 5.

4.7.3 Models

هنا نبدأ الاقتراب من UML — مثل Use Case Diagram و Sequence Diagram. وسيأتي العمق في Chapter 6.

CHAPTER 05

Data & Process Modeling

إذا Chapter 4 أجاب: «ماذا يريد المستخدم؟» — فـ Chapter 5 يسأل: «كيف تتحرك البيانات خلال النظام، وما العمليات التي تحولها؟» الفصل يصف بناء Logical Model باستخدام ثلاثة عناصر رئيسية: Data Flow Diagrams، Data Dictionary، Process Descriptions.

5.1

Logical vs Physical Models

🔴 مهم جدًا

الفرق

🧠
Logical Model — يصف: ماذا يفعل النظام؟ بدون الدخول في تفاصيل التنفيذ.
🔧
Physical Model — يصف: كيف سيتم تنفيذ النظام فعليًا؟

مثال

  • Logical: النظام يخزن بيانات العميل.
  • Physical: البيانات ستخزن في PostgreSQL على Cloud Server معين.
🎯
في Analysis نهتم أساسًا بـ Logical Model لأننا لم نقرر كل تفاصيل التصميم والتنفيذ بعد.
5.2

Data Flow Diagrams — DFD

🔴🔴 إتقان عملي كامل

من أهم أدوات Structured Analysis

DFD يوضح: كيف تدخل Data، وكيف تتحرك، وأين تخزن، وما العمليات التي تحولها.

5.3

DFD Symbols

🔴 إتقان

الأنواع الأربعة الأساسية

  • 1. Process — يمثل عملية تحول Data. مثال: Process Order.
  • 2. Data Flow — يمثل حركة البيانات. مثال: Order Details.
  • 3. Data Store — مكان تخزين Data. مثال: Customers، Orders.
  • 4. External Entity — شخص أو نظام خارج حدود النظام يتفاعل معه. مثال: Customer، Payment Gateway.

ماذا سندرس أيضًا؟

قواعد استخدام الرموز كيف نسمي Process كيف نسمي Data Flow كيف نسمي Entity كيف نسمي Data Store أخطاء الرسم التي يجب تجنبها

5.5

Context Diagram

🔴🔴 عملي

أعلى مستوى في DFD

ينظر للنظام كله وكأنه: Process واحدة كبيرة، ويظهر حولها فقط External Entities وData Flows.

مثال

Customer ← Order ← Store System ← Order Confirmation ← Customer

ماذا لا يظهر؟

تفاصيل العمليات الداخلية.

ماذا يمثل؟

System Boundary / Scope على مستوى عالٍ.

5.6

Diagram 0 DFD

🔴 إتقان

نفتح Process الكبيرة

من Context Diagram → إلى Major Processes:

Store System ← 1.0 Manage Customers ← 2.0 Process Orders ← 3.0 Manage Inventory ← 4.0 Process Payments

وتظهر: Data Stores، Data Flows، Entities.

5.7

Lower-Level DFDs

🔴🔴 إتقان

نأخذ Process واحدة ونفككها أكثر

مثلاً: 2.0 Process Order →

2.1 Receive Order 2.2 Validate Customer 2.3 Check Inventory 2.4 Calculate Total 2.5 Confirm Order

Leveling

عملية الانتقال إلى مستويات أكثر تفصيلًا.

Balancing

مبدأ بالغ الأهمية. ما يدخل ويخرج من Process في المستوى الأعلى يجب أن يتوافق مع المستوى الأدنى. لا يجوز أن تظهر Data فجأة من العدم.

Functional Primitive

عندما نصل إلى Process صغيرة كفاية ولا نحتاج تفكيكها أكثر — عندها نكتب لها Process Description بدل الاستمرار في DFD بلا نهاية.

5.8

Data Dictionary

🔴 مهم جدًا

ما هي؟

هذه ليست Database. بل قاموس مركزي يوثق عناصر النظام والبيانات المستخدمة في نماذج التحليل.

نستخدمه لتوثيق

  • Data Elements — مثل: Customer_ID، Name، Phone.
  • Data Flows — ما البيانات الموجودة داخل كل Flow.
  • Data Stores — ماذا يحتوي كل Store.
  • Processes — تعريف كل Process.
  • Entities — تعريف External Entities.
  • Records — تركيب Records.
📖
لماذا مهم؟ حتى لا يكون لدينا في Diagram: Customer ID، وفي Diagram أخرى: Customer No، وفي Document ثالث: Client Number — ولا أحد يعرف هل كلها الشيء نفسه.

5.9.3 Structured English

وسيلة لوصف Business Logic بطريقة بين اللغة الطبيعية و Programming Logic.

📝
IF customer is active
    IF product is available
        approve order
    ELSE
        notify customer
    ENDIF
ELSE
    reject order
ENDIF

الهدف ليس تعلم Programming Syntax — بل التعبير عن Business Rules بوضوح.

5.9.4 Decision Tables

ممتازة عندما يكون لدينا: عدة Conditions + عدة Actions.

YesYesYesApprove
YesYesNoReject Payment
YesNo—Notify Out of Stock
No——Reject Customer

5.9.5 Decision Trees

نفس النوع من Decision Logic لكن بشكل Tree. تفيد عندما يكون الرسم أوضح من الجدول.

ندرس متى أستخدم: Decision Table، ومتى Decision Tree، ومتى Structured English.

CHAPTER 06

Object Modeling

هنا نأخذ طريقة أخرى لفهم النظام. بدل النظر فقط إلى Data + Processes، سننظر إلى Objects تحتوي Data + Behavior. الفصل يغطي Objects و Attributes و Methods و Messages و Classes، ثم UML و Use Cases و Class/Sequence/State/Activity Diagrams.

6.1

Object-Oriented Analysis

🔴 مهم جدًا

الفكرة

ننظر إلى عناصر العالم الحقيقي ونمثلها كـ Objects. في متجر مثلًا:

Customer Product Order Payment Employee

كل واحدة يمكن أن تصبح Object أو Class في النموذج.

6.2

Objects

🔴 أساسي

تعريف Object

شيء له: Identity — Data — Behavior.

مثال: Order #251

  • له: Date، Total، Status.
  • ويستطيع: Confirm، Cancel، Calculate total.
6.3

Attributes

🟢 أساسي

خصائص Object

مثلاً Customer: customerId، name، phone، address.

❓
السؤال: ما الذي يعرفه Object عن نفسه؟
6.4

Methods

🟢 أساسي

الأفعال أو العمليات التي يستطيع Object تنفيذها

مثلاً Order: calculateTotal()، confirm()، cancel().

❓
السؤال: ماذا يستطيع Object أن يفعل؟
6.5

Messages

🟢 مهم

Objects تتفاعل مع بعضها

بإرسال Messages / Requests.

Order ← asks Customer for Shipping Address
6.6

Classes

🔴 أساسي

تعريف Class

قالب أو مجموعة Objects متشابهة. مثال: Customer = Class.

أما: Customer #125 Khalid = Instance من Customer.

مفاهيم مهمة

Class Instance Superclass Subclass Parent Child

Concepts O-O إضافية

  • Encapsulation — جمع Data + Methods داخل Object.
  • Inheritance — Subclass ترث خصائص وسلوك Superclass.
  • Polymorphism — نفس Message قد تنتج Behavior مختلف حسب Object.

هذه ليست برمجة OOP كاملة الآن؛ نحن ندرسها من منظور Analysis Modeling.

6.7

Relationships Among Objects and Classes

🔴 مهم

لا يكفي اكتشاف Classes

يجب أن نعرف: كيف ترتبط ببعض؟

  • Customer places Order.
  • Order contains Products.

Cardinality

كم Object من Class ترتبط بكم Object من Class أخرى؟

🔢
Customer: 1 → Orders: many
هذا المفهوم سيظهر أيضًا لاحقًا في Data Design.
6.8

Unified Modeling Language — UML

🔴🔴 إتقان عملي

ما هي UML؟

لغة Modeling قياسية تساعد على: Visualize + Specify + Document النظام.

6.8.1 Use Case Modeling

  • Actor — من يتفاعل مع النظام. مثل: Customer، Cashier، Manager.
  • Use Case — وظيفة أو Scenario يقوم بها Actor عبر النظام. مثل: Login، Place Order، Refund Sale، Add Product، Generate Report.

Use Case Description

لا يكفي الرسم — نوثق السيناريو. قد يشمل:

Actor Preconditions Trigger Main Flow Alternative Flow Postconditions

6.8.2 Use Case Diagram

يرسم: Actors، Use Cases، System Boundary، Relationships.

Cashier ← Process Sale ← Store Management System

6.8.3 Class Diagram

يرسم: Classes، Attributes، Relationships، Cardinality.

Customer ← Order ← OrderItem ← Product

يحول فهمنا للمجال إلى Structure واضحة للكائنات.

6.8.4 Sequence Diagram

هذه Dynamic Model — تجيب: ما ترتيب التفاعل بين Objects لتنفيذ Use Case؟

Customer ← UI ← OrderService ← Inventory ← Payment

مع الزمن من الأعلى للأسفل.

Lifeline Message Focus

6.8.5 State Transition Diagram

يعرض حالات Object وكيف ينتقل بينها.

Created ← Paid ← Shipped ← Delivered

أو: Created → Cancelled. ممتاز للأشياء التي تتغير حالتها مع الوقت.

6.8.6 Activity Diagram

يشبه Flowchart للـ Workflow.

Receive Order ← Check Stock ← [Available?] ← Process Payment / Notify Customer

6.8.7 Business Process Modeling

BPM يمكن أن يستخدم أيضًا بجانب Object Modeling؛ لأن كليهما يهتم بالـ Actors وسلوكهم وعملياتهم.
